# JVM ↔ JS 정합성

[English](parity.md)

`@devslab/ssrf-guard-js`와 [`kr.devslab:ssrf-guard`](https://github.com/devslab-kr/ssrf-guard)는
같은 보안 모델을 두 언어로 낸다. 코드도, 릴리스 라인도, 버전 번호도 공유하지
**않는다**([JS-010](decisions.ko.md#js-010--jvm-자매와-독립된-버전-라인)) — 공유하는 건
모델뿐이다. 그런데 두 구현이 여전히 일치하는지 강제하는 장치가 없다. 이 문서가
그 자리다.

**왜 필요한가.** 0.1.2 / 3.1.1의 대문자 스킴 우회는 **양쪽 모두**에 있었다. 같은
URL 수집 필터를 각각 독립적으로 작성했고, 같은 방식으로 틀렸기 때문이다. 두
구현의 어긋남은 미관 문제가 아니다 — **느슨한 쪽이 곧 구멍**이고, 그 이음매를
아무도 안 보고 있다.

## 언제 훑나

**어느 한쪽이라도** 코어 로직을 바꿀 때 — 스캐너, IP 분류, 리다이렉트 처리,
차단 사유 어휘. 어댑터나 문서 변경에는 해당 없다.

## 체크리스트

| # | 영역 | 무엇을 대조하나 |
| --- | --- | --- |
| 1 | **스캐너 수집** | 어떤 문자열이 후보가 되는가: 스킴 형태, 대소문자, 프로토콜 상대 `//host`, authority 없는 스킴, embedded(`scanEmbedded`) 패턴, 꼬리 절단 |
| 2 | **IP 분류** | 두 계열의 모든 사설/로컬 대역: IPv4 표, IPv6 표, IPv4-mapped·6to4 해제, unspecified·site-local |
| 3 | **리다이렉트 시맨틱** | 홉마다 무엇을 재검증하는가, 메서드 강등, 본문 폐기, 자격증명 제거 |
| 4 | **차단 사유** | 양쪽이 내보내는 안정된 문자열 어휘 |

**소스가 아니라 동작을 대조하라.** 두 구현을 나란히 읽는 건 애초에 0.1.2 버그가
리뷰를 통과한 방식이다. 같은 입력을 양쪽에 넣고 출력을 비교할 것.

## 감사 — 2026-08-09

첫 회차. 양방향으로 나왔다.

### 해결됨

| # | 발견 | 느슨한 쪽 | 수정 |
| --- | --- | --- | --- |
| 1 | 툴 입력 스캐너가 `http(s)://`만 수집하고, 다른 스킴은 정책이 보기 전에 버림 — `file://`·`gopher://`·`ftp://`가 조용히 통과 | **JVM** | [ssrf-guard#20](https://github.com/devslab-kr/ssrf-guard/pull/20), 미출시 3.2.0 |
| 2 | 프로토콜 상대 `//host`를 아예 수집하지 않음. 페치 시점에 호출자의 스킴을 물려받는데도 | **JVM** | 같은 PR |
| 3 | `::`(IPv6 unspecified)를 공인으로 분류 — JVM은 `isAnyLocalAddress()`로 잡음 | **JS** | 0.7.1 |
| 4 | `fec0::/10`(IPv6 site-local, RFC 3879로 폐지됐지만 구형 망에서 여전히 라우팅됨)을 공인으로 분류 — JVM은 `isSiteLocalAddress()`로 잡음 | **JS** | 0.7.1 |

1번과 2번은 이 문서를 만들게 한 그 버그와 **같은 형태**다 — *수집* 단계의
필터가, URL을 검증에서 거부되게 하는 대신 검증 자체를 빠져나가게 한다.

### 미해결

| 발견 | 느슨한 쪽 | 왜 아직 열려 있나 |
| --- | --- | --- |
| 리다이렉트 홉이 스킴 + 호스트/DNS만 재검증한다. 포트·userinfo·IP-리터럴 규칙을 다시 적용하지 않으므로, 허용된 호스트에서 `https://allowed.example:9999/`로 — 또는 공인 IP 리터럴로 — 가는 리다이렉트를 따라간다. JS는 막는다 | **JVM** | JS는 공유 루프 하나에서 홉마다 `validateUrl` 전체를 돌린다. JVM은 리다이렉트 처리가 클라이언트 어댑터 6종에 흩어져 각자 자기 클라이언트 전략에 위임한다 — 패치가 아니라 전 어댑터에 걸친 설계 변경이다 |

### 동등 확인됨

- **IPv4 사설 대역** — 집합 동일: `0.0.0.0/8`, `10/8`, `100.64/10`, `127/8`,
  `169.254/16`, `172.16/12`, `192.168/16`, `198.18/15`, 브로드캐스트.
  멀티캐스트는 양쪽 다 커버하되 JS는 v4 표에서, JVM은 `InetAddress` 레벨에서.
- **IPv4-mapped(`::ffff:`)·6to4(`2002::/16`) 해제** — 양쪽 다 내장된 v4 주소를
  재분류하므로 `::ffff:10.0.0.5`와 `2002:0a00::1`이 양쪽에서 차단된다.
- **대문자 스킴** — 양쪽 다 수정됨(0.1.2 / 3.1.1). 재확인 완료.
- **차단 사유 어휘** — `blocked_response_size` 하나만 빼고 동일. 그건 `maxBytes`가
  JS 전용 기능이라 JS에만 있다([JS-015](decisions.ko.md#js-015--maxbytes는-자르지-않고-차단한다)).
  JVM에 대응 기능이 생기면 이 사유도 필요하다.

### 방법

3·4번은 추론이 아니라 **실측**이다. 두 소스를 읽고 판단한 게 아니라, 주소 목록을
빌드된 패키지에 넣어 돌리고 JVM 헬퍼가 주는 답과 대조했다. 추론은 애초에 원래
버그를 만들어낸 방식이다.

```
false ::          ← JVM: isAnyLocalAddress() → true
false fec0::1     ← JVM: isSiteLocalAddress() → true
```

## 의도적으로 다른 것

전부 같아야 하는 건 아니다. 아래는 의도된 차이다:

- **`maxBytes` / `blocked_response_size`** — 아직 JS 전용.
- **`checkUrl` / `isUrlAllowed`** — JS 전용. JVM에는 예외를 던지지 않는 판정
  API가 없다.
- **`singleHostPolicy` / `sameSitePolicy`** — JS 전용.
- **어댑터** — JVM이 HTTP 클라이언트 모듈 6종을 내는 건 그 클라이언트들이 요청
  실행을 소유하기 때문이다. JS는 `fetch`를 감싸므로 하나면 된다([로드맵](roadmap.ko.md)).
- **버전 번호** — [JS-010](decisions.ko.md#js-010--jvm-자매와-독립된-버전-라인).

JS 전용 기능이 있는 건 정합성 실패가 아니다. **JVM에도 있는데 다르게 구현된 것**이
실패다.
