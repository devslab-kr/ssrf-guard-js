## JS-001 — 기본값은 fail-closed 호스트 허용 목록

**출시:** 0.1.0 (2026-06-18)

**맥락.** SSRF 가드는 기본값만큼만 좋다. 설정하기 전까지 전부 허용하는
라이브러리는 설정을 잊은 사람을 전혀 보호하지 못하는데, 가드가 필요한 모집단이
바로 "설정을 잊은 사람"이다.

**결정.** `exactHosts`와 `suffixes`가 비어 있으면 **어떤 호스트도 허용하지
않는다**. "모든 호스트 허용" 스위치는 없다. 호스트를 여는 방법은 허용 목록에
넣는 것뿐이고, 그래서 모든 예외가 한 곳에서 감사된다. 사설 대역·IP 리터럴
호스트·userinfo도 기본 거부다.

**대안.** 관대한 기본값 + 옵트인 strict 모드(흔한 형태), 알려진 악성 표적
(메타데이터 IP·RFC1918) 거부 목록.

**트레이드오프.** 첫 사용의 마찰이 크고, 임의 URL이 정말 필요한 호출부는
요청마다 정책을 파생해야 한다 — 그게 `sameSitePolicy`의 용도다
([JS-007](#js-007--samesitepolicy는-앞의-www를-제거한다)). 거부 목록이 더
친절했겠지만 틀렸을 것이다: 문제가 되는 표적은 아무도 열거하지 않은 쪽이다.

**재검토 시점.** 기본값은 영구히 유지. 임의 URL 페치가 진짜 유스케이스가 되면
기존 API의 플래그가 아니라 **별도로 명명되고 별도로 문서화된 API**로 낸다.

## JS-002 — 툴 입력 스캐너는 http(s)만이 아니라 모든 스킴을 수집한다

**출시:** 0.2.0 (2026-07-05)

**맥락.** 스캐너가 `http://`와 `https://` 문자열만 수집해서, LLM 툴 입력의
`file://`·`ftp://`·`gopher://` URL이 조용히 통과했다 — 검증 자체가 안 되니
`allowedSchemes`가 거부할 기회조차 없었다.

**결정.** **모든** `scheme://` URL을 수집하고 판단은 정책에 맡긴다.
프로토콜 상대 `//host` 문자열도 수집해 호스트 정책으로 검증한다. authority가
없는 스킴(`mailto:`·`urn:`·`data:`)은 계속 무시한다 — 검사할 호스트가 없다.

**대안.** 하드코딩된 스킴 목록 확장, 비-http 스킴은 호출부에 위임.

**트레이드오프.** 명백히 더 엄격해졌고 — 통과하던 입력이 이제 위반이 된다 —
그래서 마이너 범프에 주의 문구와 함께 실었다. 이제 수집과 정책이 깔끔히
분리된다: 수집은 관대하게, 판단은 정책이.

**재검토 시점.** authority 없는 스킴 중 호스트급 검증이 필요한 정당한 사례가
나올 때.

## JS-003 — 공인+사설 혼합 DNS 응답은 fail-closed

**출시:** 0.2.0 (2026-07-05)

**맥락.** `safeFetch`는 해석된 주소 중 **하나라도** 공인이면 허용했다. DNS
레코드를 통제하는 공격자가 공인 주소와 사설 주소를 함께 반환하면, 검사는 공인
주소로 통과하고 실제 연결은 사설 주소로 갈 수 있었다.

**결정.** 해석된 주소 중 **하나라도** 사설/로컬이면 차단한다.

**대안.** any-public 규칙을 유지하고 DNS 피닝
([JS-005](#js-005--선택적-undici-peer-의존성을-통한-dns-피닝))으로 막기 — 당시
피닝은 아직 없었고, 지금도 선택 사항이다.

**트레이드오프.** split-horizon DNS를 정당하게 쓰는 호스트에 도달할 수 없게
된다. 감수한다: 보안 라이브러리이고, 그 구성은 이 공격에 비하면 드물다.

**재검토 시점.** 오탐이 실제 배포에 해가 된다는 증거가 나오기 전엔 없음.

## JS-004 — fetch 스펙 리다이렉트 시맨틱, 교차 출처 자격증명 미전달

**출시:** 0.2.0 (2026-07-05)

**맥락.** `safeFetch`가 리다이렉트를 건너 헤더와 본문을 재전송했다. 공격자
통제 출처로의 리다이렉트가 호출자의 `Authorization`·`Cookie`를 그대로 실어
갔고, 원래 `POST` 본문도 다시 보냈다.

**결정.** 리다이렉트로 출처가 바뀌면 `Authorization`·`Proxy-Authorization`·
`Cookie`를 제거하고, fetch 스펙을 따른다: `303`(그리고 `POST`의 `301`/`302`)은
`GET`으로 강등하고 본문을 버린다.

**대안.** 신뢰하는 리다이렉트 체인에서 자격증명을 유지하는 옵션.

**트레이드오프.** 재전송에 의존하던 호출부는 후속 요청을 직접 보내야 한다.
아무도 예측할 수 없는 자체 규칙보다 플랫폼의 시맨틱을 따르는 편이 낫다.

**재검토 시점.** 없음 — 이게 스펙이다.

## JS-005 — 선택적 `undici` peer 의존성을 통한 DNS 피닝

**출시:** 0.3.0 (2026-07-05)

**맥락.** check-then-fetch에는 TOCTOU 창이 있다. 가드가 호스트를 해석하고,
`fetch`가 다시 해석하며, DNS 리바인딩으로 두 답이 달라질 수 있다. 창을 닫으려면
소켓 커넥터 안에서 검증해야 하고, 그러려면 실제 HTTP 에이전트가 필요하다.

**결정.** `undici`를 **선택적** peer 의존성으로 둔다. 있으면 커넥터 안에서
검증해 검사와 연결이 하나의 해석을 공유하고(JVM Apache HttpClient 어댑터와
같은 소켓 레벨 피닝), 없으면 check-then-fetch로 폴백한다. `pinDns: true`는
피닝을 요구하고 `undici` 없이는 예외를 던지며, `false`는 폴백을 강제하고,
미지정이면 자동 감지한다.

**대안.** `undici` 하드 의존(`validateUrl`만 쓰는 소비자까지 무게와 버전 결합을
떠안는다), 자체 에이전트 구현, 창을 그냥 열어두기.

**트레이드오프.** 가장 강한 보장이 소비자가 무언가를 설치해야만 켜지고, 문서가
계속 그 사실을 말해야 한다. 대신 URL 정책과 툴 가드만 쓰는 다수 —
실제 다수다 — 에게는 패키지가 의존성 없이 남는다.

**재검토 시점.** `undici`가 평범한 의존성으로 둘 만큼 보편화되거나, 플랫폼이
커넥터 레벨 훅을 기본 제공할 때.

## JS-006 — degraded `safeFetch` 대신 `guardedFetch` 분리

**출시:** 0.4.0 (2026-07-13)

**맥락.** `safeFetch`는 연결 전에 `node:dns/promises`의 `lookup`으로 대상을
해석한다. Cloudflare Workers에서 `lookup`은 `Not implemented`를 던지고, 설령
해석된다 해도 Workers `fetch`는 내부적으로 자체 해석을 하므로 유저랜드가 검사한
IP를 소켓에 고정할 수 없다. check-then-fetch 간극은 Worker 안에서 닫을 수 없다.

**결정.** 두 번째 함수를 낸다. `guardedFetch`는 URL 시점 검증·홉별 리다이렉트
재검증·자격증명 제거·메서드 강등 시맨틱을 유지하고 DNS 검사를 **뺀다**.
`node:dns`가 없는 런타임에서 `safeFetch`는 임포트 시점이 아니라 호출 시점에
`guardedFetch`를 가리키는 타입 있는 `SsrfGuardError`를 던진다. `node:dns`는
지연 임포트라 패키지 임포트 자체는 언제나 안전하다.

**대안.** DNS 검사를 조용히 건너뛰기 — 그러면 같은 호출이 실행 위치에 따라 다른
보장을 의미하게 되고, 보안 통제가 조용히 장식으로 전락하는 경로가 그것이다.

**트레이드오프.** 설명할 함수가 둘이 되고, 어떤 보장이 어느 런타임에서
살아남는지 못 박는 README 표가 필요해졌다. 그만한 값어치가 있다 — 약한 보장이
호출부에서 이름으로 드러난다.

**재검토 시점.** Workers가 쓸 수 있는 `lookup` **그리고** 해석된 주소를 연결에
고정할 방법을 함께 제공할 때. 둘 다여야 하고, 아니면 바뀌는 건 없다.

## JS-007 — `sameSitePolicy`는 앞의 `www.`를 제거한다

**출시:** 0.4.0 (2026-07-13)

**맥락.** "고객 자기 사이트 크롤"에는 제출된 URL에서 파생한 요청별 정책이
필요하다. 실제 사이트는 apex ↔ `www` 리다이렉트를 끊임없이 하고, 제출된 호스트에
정확히 고정된 정책은 첫 홉에서 깨진다.

**결정.** 제출된 URL에서 앞의 `www.`를 뗀 허용 목록을 파생해 apex와 `www`를 한
사이트로 본다. 오버라이드는 가산 병합이라 다른 호스트를 함께 열 수 있다.

**대안.** 정확한 호스트만(리다이렉트에서 깨진다), public suffix list 기반
등록가능 도메인 매칭(`www`로 커버되는 사례를 위해 의존성과 갱신해야 할 데이터
파일을 떠안는다).

**트레이드오프.** `www.`를 이름으로 특례 처리하는 것이라 규칙이 아니라
휴리스틱이다. 정확한 호스트만 원하는 호출부는 지금 정책을 손으로 다시 만든다 —
`singleHostPolicy` 헬퍼가 [로드맵](roadmap.ko.md#p2--singlehostpolicybaseurl)에
있다.

**재검토 시점.** 다른 관용 접두사가 실제로 문제가 되거나, 진짜 등록가능 도메인
범위가 필요한 소비자가 나올 때.

## JS-008 — `scanEmbedded`는 옵트인

**출시:** 0.5.0 (2026-07-30)

**맥락.** 기본 스캐너는 trim된 값 전체가 URL인 문자열만 잡는다. 모델에게
`"summarize http://169.254.169.254/ please"`를 시키면 메타데이터 URL이 산문 속에
숨어 통과한다.

**결정.** 인자 문자열 **어디에 묻혀 있든** URL을 추출하되, 옵트인 플래그 뒤에
둔다. 명백히 가산적이다 — 기본 스캐너가 잡던 것은 전부 그대로 잡힌다. 자기
범위 안에서는 의도적으로 공격적이다: 산문이나 코드 조각 안의 URL도 검증하므로
예시 안의 비허용 호스트도 위반으로 센다. URL 꼬리에 붙은 산문 문장부호는
잘라내고, 경로 안의 짝 맞는 괄호는 보존한다.

**대안.** 기본 활성화(모든 소비자에게 조용히 더 엄격해진 마이너 릴리스가 되고,
코드 조각·문서 인용 도구가 명백한 오탐 모집단이다), 주변 텍스트가 산문인지
코드인지 추측하는 휴리스틱 — 예측 가능성이 가장 필요한 상황에서 예측 불가능해
진다.

**트레이드오프.** 더 안전한 동작이 요청해야만 켜지므로, 문서를 안 읽은 사람은
약한 스캔에 머문다. 감수한다 — 이 옵션은 설계상 공격적이고, 켜는 것은 자기 툴
입력에 대한 결정이며, 결정이어야 마땅하다.

**재검토 시점.** 현장 데이터로 오탐률이 충분히 낮다고 확인되면 메이저에서 기본
값을 뒤집는다.

## JS-009 — `Response.url` 대신 `onFinalUrl`

**출시:** 0.5.0 (2026-07-30)

**맥락.** 리다이렉트를 따라간 뒤, 호출부는 콘텐츠가 실제로 온 URL이 필요하다 —
출처 표시, 저장 키. 명백한 출처인 `Response.url`은 신뢰할 수 없다: 커스텀
`fetchImpl`과 테스트 페이크는 비워둘 수 있고, 리다이렉트 이후 빈 값은 콘텐츠에
**제출된** URL을 조용히 잘못 붙인다.

**결정.** 모든 홉을 따라간 뒤 **가드가 검증한** 최종 URL로 호출되는 콜백을
`guardedFetch`와 `safeFetch` 양쪽에 둔다. fetch가 던지면 호출되지 않는다.

**대안.** 래퍼 객체 반환(파괴적 — 반환 타입이 평범한 `Response`다),
`Response.url`을 문서화하고 폴백을 소비자에게 맡기기 — 소비자가 이미 그렇게
하다 틀렸던 지점이다.

**트레이드오프.** 값 하나를 콜백으로 받는 건 어색한 모양이고, 반환 타입을
`Response`로 유지하려다 강제된 형태다. 또한 fetch 구현이 아니라 가드의 관점을
보고한다 — 그게 요점이지만 알고 쓸 일이다.

**재검토 시점.** 다른 이유로 options-in/result-out 형태의 fetch API가 생기면
거기에 흡수한다.

## JS-010 — JVM 자매와 독립된 버전 라인

**출시:** 0.1.0부터 암묵적으로

**맥락.** `kr.devslab:ssrf-guard`는 "라이브러리 major = Spring Boot major"라는
org 규칙에 따라 `3.x.y`다. 이 패키지에는 Spring Boot가 없고, 더 늦게 더 작은
표면으로 시작했다.

**결정.** `@devslab/ssrf-guard-js`는 자기 성숙도에 따라 자기 `0.x` 라인으로
버전을 매긴다. 두 라이브러리는 보안 모델을 공유하고 README에서 상호 링크하지만
릴리스 라인은 공유하지 않으며, 버전 번호는 기능 동등성의 약속이 아니다.

**대안.** JVM 버전 미러링(여기선 무의미 — 그 숫자는 Spring Boot major를
인코딩한다), 릴리스 동기화(소비자도 주기도 다른 두 코드베이스를 묶는다).

**트레이드오프.** "같은 버전 = 같은 기능"을 유추할 수 없다. 그 역할은 각
CHANGELOG와 README의 Family 섹션이 대신한다.

**재검토 시점.** 1.0 — 그때 동등성이 무엇을 뜻하고 무엇을 뜻하지 않는지 명시할
가치가 있다.

## JS-011 — TypeScript 7은 빌드 툴체인에만

**출시:** 0.5.1 (2026-08-08, PR #15로 2026-07-30 머지)

**맥락.** TypeScript 7의 네이티브 컴파일러는 눈에 띄게 빠르다. 다만 타입이 곧
공개 표면인 라이브러리에서 이를 도입하면 생성되는 선언 파일이 달라질 위험이
있고, 그건 소비자 대상 파괴적 변경이다.

**결정.** **빌드** 툴체인만 옮긴다: `typescript` `^5.9.3` → `^7.0.2`,
`tsdown`은 `.d.ts` 생성에 TS 7을 허용하는 첫 peer 범위 버전으로. 배포 산출물·
타입 선언·소비자가 쓸 수 있는 TypeScript 버전은 그대로다.

**대안.** 생태계를 기다리기, 소비자 대상 TypeScript 하한도 함께 올리기(소비자
이익 없는 파괴적 변경).

**트레이드오프.** 툴체인이 새 메이저에 일찍 의존하게 되고, "소비자 영향 없음"
이라는 주장은 산출물이 동일하다는 데 기댄다 — 그러니 범프마다 가정하지 말고
확인해야 한다.

**재검토 시점.** 소비자 대상 TypeScript 하한 상향을 그 자체의 근거로 제안할 때.

**재검토 시점.** 문서 사이트에 공개 계획 페이지가 생겨 이 파일들이 그 소스가
될 때.

## JS-013 — 머지가 곧 릴리스

**날짜:** 2026-08-08 (0.5.1과 함께 출시)

**맥락.** `Publish to npm`은 `vX.Y.Z` 태그 푸시에만 걸렸다. 그래서 릴리스마다
머지 뒤에 로컬 `git tag` + `git push`가 필요했다. org의 다른 것들은 전부 `main`
머지에서 배포되고, 이 repo의 문서 사이트조차 이미 그렇다. 게다가 태그 단계는
에이전트가 수행할 수 없는 유일한 구간이라, 0.5.1이 머지된 채 사람이 명령 하나
실행하기를 기다리며 미출시로 남아 있었다.

**결정.** `package.json`의 `version`이 아직 npm에 없는 `main` push에서
출시한다. 워크플로가 검증하고, 배포하고, 태그를 스스로 만들고, CHANGELOG
섹션으로 GitHub Release를 연다. 손으로 미는 태그도 그대로 동작하고, 여전히
`package.json`과 일치해야 한다.

**게이트는 태그가 아니라 npm 레지스트리다.** 이 선택이 실질적인 일을 한다 —
평범한 머지는 조용한 no-op이 되고, 잡이 멱등해져서 부분 실패 뒤 재실행해도
이중 배포가 불가능하다. 태그 존재로 게이트했다면 실패 양상이 뒤집힌다:
태그를 만든 **뒤** 배포가 실패하면 이후 모든 실행이 조용히 스킵되는데, 릴리스가
망가지는 방식 중 최악이다. 그래서 태그는 배포 성공 뒤에 붙인다. 남는 간극
(배포됨·태그 없음)은 다음 실행에서 조용히 넘어가지 않고 시끄럽게 실패한다.

**대안.** 태그 트리거 유지 + 릴리스는 소유자 전용으로 인정하기, `changesets`
/ `release-please`(Release PR 봇 — 몇 주에 한 번 내는 패키지엔 과한 기계),
main-push 워크플로가 태그만 만들고 기존 태그 워크플로가 배포하게 하기 — 이건
아예 동작하지 않는다. `GITHUB_TOKEN`으로 민 태그는 워크플로를 트리거하지 않기
때문이다.

**트레이드오프.** 태그 푸시는 되돌릴 수 없는 npm 배포 직전의 마지막 수동
게이트였고, 그게 사라진다. 이제 머지된 PR의 버전 번호가 틀리면 즉시 배포된다.
그 자리에 남는 것은 PR 리뷰와 배포 단계 앞에서 도는 `pnpm verify`뿐이다 —
사람이 태그 앞에서 멈추는 것보다 약하고, 자동화를 위해 의도적으로 감수한다.

**재검토 시점.** 이 경로로 잘못된 버전이 실제로 npm에 나가거나, 릴리스 주기가
느려져 수동 게이트의 비용이 무의미해질 때.

## JS-014 — 예외 없는 판정은 `validate`를 다시 구현하지 않고 잡는다

**출시:** 0.6.0 (2026-08-08)

**맥락.** `validateUrl`은 던지고 `HostPolicy.allows()`는 호스트만 본다. 그래서
"이 URL을 시도라도 해야 하나"를 판단하는 호출부 — 크롤러가 큐에 넣을 링크,
여러 URL 중 거부로 보고할 것 — 에게 정책 모양의 API가 없었다. AskLinq 크롤러는
대신 `target.hostname !== base.hostname`을 썼고, 이는 `sameSitePolicy`와
어긋난다. `www.` 제거 때문에 **fetch 가드였다면 허용했을** apex ↔ `www` 링크가
시도조차 되기 전에 버려졌다.

**결정.** `checkUrl`(`{ allowed, url | error }` 반환)과 `isUrlAllowed`,
그리고 `UrlPolicy.check()`를 추가한다. 구현은 검사를 다시 유도하지 않고
**`validate`를 잡아서** 한다.

**구현 방식 자체가 결정이다.** 두 번째 구현은 언제든 어긋날 수 있고, 가드와
불일치하는 판정 API는 없느니만 못하다 — 호출부를 **틀린 답에 대해 확신하게**
만들기 때문이다. 이건 0.1.2 우회와 같은 실패 형태다. 그때도 따로 작성된 URL
수집 필터가 하위의 스킴 검사와 어긋났다. 두 경로가 일치한다는 성질을 입력
매트릭스 테스트로 못 박아, 의도에 그치지 않게 했다.

**대안.** boolean만 반환(사유를 잃는다 — 로깅에 필요하다), 거부 시 `null`
반환(같은 손실), 속도를 위해 분기 없는 형태로 검사 중복(아무도 측정하지 않은
비용을 위해 드리프트 위험을 떠안는다).

**트레이드오프.** 거부되는 URL마다 내부적으로 예외를 만들고 던지므로 단순 비교
보다 느리다. 크롤러 규모의 링크 필터링에서는 무의미한 차이이고, 대신 판정
API와 가드가 **절대 불일치할 수 없다**는 보장을 산다.

**재검토 시점.** 호출부가 이걸 실제 비용으로 프로파일링할 때 — 그때의 해법은
정책별 메모이제이션이지 두 번째 구현이 아니다.

## JS-015 — `maxBytes`는 자르지 않고 차단한다

**출시:** 0.6.0 (2026-08-08)

**맥락.** AskLinq의 두 호출부 모두 `await res.text()`가 본문을 **이미 전부**
끌어온 **뒤에** 크기를 잘랐다(`BRIDGE_RESPONSE_MAX_CHARS`, `MAX_BODY_CHARS`).
그건 보호가 아니라 표시상의 편의다 — 바이트는 이미 전선을 건넜고, 끝없이
흘려보내는 엔드포인트는 여전히 호출부를 고갈시킨다.

**결정.** `guardedFetch`와 `safeFetch`에 `maxBytes` 옵션을 두고 **두 군데**에서
강제한다. 한쪽만으로는 부족하기 때문이다 — `Content-Length`가 상한을 넘으면 한
바이트도 읽기 전에 거부하고, 그 헤더를 생략하거나 축소한 응답은 스트리밍 중
누적 카운트가 잡는다. 초과는 신규 `blocked_response_size` 사유의
`SsrfGuardError`다.

**자르지 않고 차단하는 이유.** 신호 없이 짧은 본문을 받은 호출부는 부분 문서를
전체로 취급하고, 그 순간 크기 제한이 정합성 버그로 바뀐다 — 게다가 조용한 부분
읽기는 테스트에서 멀쩡해 보이는 종류의 사고다. 잘라 쓰고 싶은 호출부는 에러를
잡아 **명시적으로** 그렇게 선택하면 된다.

**대안.** 자르고 응답에 플래그 세우기(아무도 안 보는 플래그는 단계만 늘린 조용한
잘림이다), `Content-Length`만 검사(헤더를 빼면 그만이다), 본문을 전부 버퍼링한
뒤 검사(그게 바로 이번에 대체하는 우회다).

**트레이드오프.** 상한이 적용된 응답은 **새** `Response` 객체라 `url`·
`redirected`·`type`을 잃는다 — `onFinalUrl`
([JS-009](#js-009--responseurl-대신-onfinalurl))로 완화되고, 어차피 그쪽이
`Response.url`보다 신뢰할 수 있다. `BlockReason` 추가는 이 union을 빠짐없이
분기하는 소비자를 깨뜨리므로 마이너 범프로 냈다. 그리고 잘못된 `maxBytes`는
강제 변환하지 않고 요청 전에 `TypeError`로 던진다 — `Number(process.env.X)`에서
온 `NaN`은 그러지 않으면 모든 크기와의 비교에서 false가 되어 상한을 조용히
꺼버린다.

**재검토 시점.** 에러를 잡는 게 실질적인 마찰이 될 만큼 잘림 모드 수요가
잦아질 때 — 그때는 이 옵션을 바꾸는 게 아니라 별도로 명명된 옵션을 추가한다.

## JS-016 — 가드는 호스트가 훅을 존중해 주는 데 기대면 안 된다

**출시:** 0.6.1 (2026-08-08)

**배경.** `safeFetch`의 핀 모드는 사설 IP 규칙을 `undici`의
`Agent({ connect: { lookup } })`에 넘긴 콜백 **안에서만** 강제했고, 커넥터가
어차피 검사하니 사전 검사는 **의도적으로 생략**했다. 검사와 소켓이 하나의
resolution을 공유하는 것 — 그게 피닝의 존재 이유다
([JS-005](#js-005--선택적-undici-peer-의존성을-통한-dns-피닝)).

Bun 1.3.3은 그 옵션을 받아들이고 콜백을 **한 번도 부르지 않는다.** 두 검사 중
어느 것도 실행되지 않았다. 루프백에 실제 리스너를 띄운 상태에서 Bun의
`safeFetch`는 `127.0.0.1`로 resolve되는 호스트에 HTTP 200을 돌려줬다 — 이
라이브러리가 거부하려고 존재하는 바로 그 요청이다. Node와 Deno는 훅을 존중하며
영향이 없었다.

런타임 특이사항으로 끝나지 않은 이유가 둘이다. 이것이 **기본값**이었다 —
`pinDns`를 지정하지 않으면 `undici`가 깔려 있기만 해도 핀이 켜지므로, 아무것도
선택하지 않은 사람이 가드를 잃었다. 그리고 **하드닝 옵션을 뒤집었다** —
신중한 호출부가 손을 뻗는 `pinDns: true`가 사설 IP 검사를 끄는 가장 확실한
방법이었다.

테스트 스위트에도 보이지 않았다. 핀 모드 테스트가 Node에서 전부 통과한 것은
**바로 Node가 훅을 부르기 때문**이다. 훅이 동작하는 곳에서만 도는 스위트는,
훅이 동작하지 않는 곳에서만 존재하는 버그를 관측할 수 없다.

**결정.** 사전 DNS 검증을 핀 여부와 무관하게 **모든 모드에서** 실행한다. 피닝은
이제 순수하게 가산적이다 — 훅을 존중하는 런타임에서는 여전히 검사와 연결을 한
resolution으로 합쳐 리바인딩 창을 닫고, 그렇지 않은 런타임에서도 사설 IP 가드는
그대로 선다.

일반화된 규칙, 그리고 이게 체인지로그 한 줄이 아니라 결정 항목인 이유:
**보안 통제가 남의 콜백 안에 있을 때, 그것이 자기 자신의 유일한 사본이어서는
안 된다.** 선택적 훅은 호스트에 대한 요청이지 호스트의 보장이 아니다. 훅을
무시하는 호스트는 안쪽에서 탐지할 수 없다 — 콜백이 그냥 안 불릴 뿐이고, 그건
애초에 부를 필요가 없던 요청과 구분되지 않는다.

**비용.** 피닝을 존중하는 런타임에서 홉당 DNS 조회가 한 번 는다. 주소를 두 번
찾기 때문이다. 그게 보장이 조건부가 되지 않는 값이고, 비핀 모드는 이미 치르던
비용이다. 리졸버 캐시가 대부분 흡수한다.

**대안.** 시작 시 훅이 실제로 불리는지 탐침하고 아니면 fail-closed(첫 사용에
네트워크 왕복이 붙고, 탐침이 모든 런타임의 동작을 모델링해야 한다), 무시한다고
알려진 런타임에서는 핀을 거부(Bun이 고치는 순간, 또는 다음 런타임이 나오는
순간 틀리는 denylist), 그대로 두고 Bun을 미지원으로 문서화(실패가 조용하고
기본값이 켜져 있다 — 문서는 그걸 읽지 않은 사람에게 닿지 않는다).

**테스트.** 회귀 테스트는 `connect.lookup`을 받아들이고 무시하는 `Agent`로
`undici`를 목킹해, 적대적 런타임을 Node 스위트 안에서 재현한다. `pinDns: true`,
자동 피닝, 리다이렉트 홉 세 경우 모두에서 차단이 유지되는지 확인하고, 스텁이
실제로 훅을 건네받았는지도 확인한다 — 테스트가 엉뚱한 이유로 통과하지 못하게.

**재검토 시점.** Bun이 `connect.lookup`을 존중하기 시작할 때. 그때도 사전 검사는
남긴다. 요점은 보장이 밑에 깔린 런타임에 좌우되지 않는다는 것이다.
